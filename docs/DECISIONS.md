## 2026-09-23: Offline Pre-Caching Layer
- **Context:** Issue : `apps/service-worker/` was an empty folder; nothing was actually registered or precached, despite being on every slide since Iteration 1.
- **Prerequisite gaps found and fixed:** there was no `index.html` or `src/main.tsx` entry point at all - the app had never been served as an actual page, only rendered inside test harnesses. Added both, plus a real `manifest.json` (was previously a 0-byte file) and a legitimate SVG app icon.
- **Data reachability:** `data/geojson/route.geojson` and `waypoints.geojson` lived outside `apps/web/public/`, so the browser could never fetch them at runtime. Copied both into `apps/web/public/data/` so `MapCanvas` and the service worker can actually use them. **This creates a duplicate source of truth** - the two copies will drift if one is edited without the other. Recommend either making `apps/web/public/data/` the single source, or adding a small build step that copies from `data/geojson/` automatically, before Iteration 4.
- **Service worker location:** built at `apps/web/public/sw.js`, not inside a top-level `apps/service-worker/` folder - Vite only serves static files out of `apps/web/public/`, so that's the only path from which `navigator.serviceWorker.register()` can get full page scope.
- **Station media precache is deliberately empty:** the 4 anchor stations still have no real Memory Vault images or Audio Capsule audio files (`MemoryVaultSlider` renders emoji/CSS placeholders, and no audio-capsule data file exists at all). Listing invented file paths in the precache manifest would make `cache.addAll()` fail its entire install step on the first 404. `STATION_MEDIA_ASSETS` in `sw.js` is a ready, empty array with a loud comment - add real URLs there once the content pipeline produces real files.
- **Map tile precache:** computed the real install-time tile set from the actual corridor bounding box in `route.geojson`, at zoom 5 only (4 tiles per tile layer, 8 total) - both for the OSM base layer and the terrain-RGB elevation layer. Deliberately narrow: `tile.openstreetmap.org`'s usage policy prohibits bulk tile downloading, so this stays a small, demo-safe slice. A production deployment should move to a proper tile provider (MapTiler/Mapbox/self-hosted) before caching a wider range.
- **Tile math duplication:** the zoom/tile computation exists in two places - the tested, canonical `apps/web/src/lib/tileMath.ts`, and a plain-JS mirror inside `public/sw.js` (which can't import TypeScript modules without a bundler plugin we don't have installed, e.g. `vite-plugin-pwa`). If the tile algorithm changes, both need updating. Worth revisiting with `vite-plugin-pwa` in a later iteration to remove this duplication and get a build-time-injected precache manifest for free instead of a hand-maintained one.

## 2026-09-23: SHA-256 Integrity Manifest
- **Found while starting this ticket:** `apps/web/public/data/route.geojson` was present but 0 bytes, and `waypoints.geojson` was missing entirely - there was a `waypoint.geojson` (singular, wrong name) that was also 0 bytes. Both were re-copied from the real source at `data/geojson/` at the repo root. Worth a reminder to the team: the duplication flagged in the Issue #6 entry above is exactly how this kind of drift happens - a copy step done by hand, once, that silently goes stale or gets fumbled on a re-copy.
- **Scope decision:** the integrity manifest covers `manifest.json`, `icon.svg`, and the three data files (`route.geojson`, `waypoints.geojson`, `memory-vault.json`) - not `index.html` or `/`. Vite transforms `index.html` differently between dev (injects the HMR client) and a production build, so its bytes aren't stable/hashable the same way; the STRIDE slide's own wording ("protect cached assets... from malicious injection into **offline archives**") is about archive/data content, not the app shell, which has its own separate protection story via HTTPS and Vite's content-hashed bundle filenames.
- **Generated, not hand-maintained:** `apps/web/scripts/generate-integrity-manifest.mjs` runs automatically via `predev`/`prebuild` npm hooks, writing `public/integrity-manifest.json` fresh every time. Deliberately not committed-and-trusted the way `package-lock.json` is - if this project later adds a CI step, verifying the manifest is up-to-date by regenerating and diffing would be a good addition rather than trusting whatever's in git.
- **Verification only applies to cache-serving path, not the network path:** by DoD wording, this checks a *fetched-from-cache* asset's hash before serving it; a fresh network response isn't hash-checked (map tiles and live API responses were already excluded from this list entirely - see the ASSET_PATHS/STATIC_INTEGRITY_ASSETS comments in the generator script and sw.js).
- **Tile hashing out of scope:** map tiles aren't in the integrity manifest - they're cross-origin, fetched opaquely (`no-cors`), and their bytes can't be read/hashed from an opaque response at all, so this wouldn't be technically possible without switching tile providers to something CORS-enabled.

## 2026-09-25: Server-Side Passport & Traveler-Rank Validation Hardening (Issue #18)
- **Context:** direct implementation of the STRIDE "Elevation of Privilege" mitigation from the security slide - traveler rank must never be trusted from the client.
- **Found already substantially in place:** Issue #27's earlier work already computed rank and stamps exclusively server-side (`db/session_store.get_passport`) from an in-memory per-session stamp ledger, so DoD item 1 (`GET /passport/{sessionId}` reflects only server-verified trivia results) was already satisfied before this pass started.
- **Gap closed - explicit rejection, not incidental:** there was no `POST /passport/{sessionId}` route at all, so a POST there already fell through to Starlette's default 405 - correct behavior, but implicit and untested, meaning a future change could silently add a mutating handler on that path without anything failing. Added an explicit `POST /passport/{session_id}` handler in `routers/passport.py` that always raises `405` with a message pointing callers at the real, validated path (`POST /waypoints/{waypointId}/trivia/answer`), so the rejection is a documented, intentional decision covered by a test rather than routing table trivia.
- **Second bypass vector closed:** the DoD wording ("bypassing trivia") covers more than a direct `POST /passport`. `schemas/trivia.AnswerSubmission` already has `extra="forbid"`, so a request that answers correctly *and* smuggles a `"rank": "Rail Legend"` field into the same body was already rejected with `422` - added an explicit test for this rather than leaving it to be an accidental side effect of an unrelated schema choice.
- **Testing standard (Rule 6):** added `tests/test_passport_security.py`, covering all three DoD checkboxes directly: (1) a fresh session starts at `Stoker`/zero stamps and rank only progresses through four legitimately-answered trivia questions, ending at `Rail Legend` with `totalScore == 400`; (2) `POST`/`PUT`/`DELETE` against `/passport/{sessionId}` all return `405` and leave the session's real state untouched; (3) a `POST` with a fabricated `"rank": "Rail Legend"` payload (the exact DoD example) is rejected and the session still reads back as `Stoker`. Also added a defense-in-depth check that `GET /passport/{sessionId}` ignores `rank`/`score` passed as query-string parameters, since nothing about the route reads them today, but that wasn't locked in by a test before.
- **Scope decision:** the DoD only calls out `POST`; `PUT`/`DELETE` are covered by Starlette's default per-path-method-set 405 without needing dedicated handlers (only `GET` and the new explicit `POST` are registered on `/passport/{session_id}`), verified by test rather than by adding more unused handlers.

## 2026-09-26: ANU Quantum Random Number Server Integration 
- **Context:** Issue #39: add a genuine quantum-tech integration to satisfy the "Use of Quantum Tech" bonus criterion honestly, scoped to shuffling displayed trivia answer-option order only.
- **Integration point confirmed by inspection, not assumed:** there is no standalone `TriviaPrompt.tsx` in this codebase - trivia (Issue #36's follow-on work) renders inline inside `MemoryVaultSlider.tsx`'s vault card, driven by `triviaQuestion`/`onTriviaRequest` props owned by `UnifiedViewport.tsx`. The shuffle was wired into that existing panel rather than introducing a parallel component that would fork the trivia UI in two directions. Two stray empty files (`components/TriviaPrompt.tsx`, `components/__tests__/TriviaPrompt.test.tsx`) were found unreferenced anywhere in the codebase and removed rather than populated, to avoid forking the trivia UI into two places.
- **Entropy source, not a security boundary:** `lib/quantumRandom.ts`'s `quantumShuffle()` fetches `n-1` true-random bytes from the ANU QRNG API (`https://qrng.anu.edu.au/API/jsonI.php`) in a single request per question and runs a Fisher-Yates shuffle over the answer options. No answer-submission flow exists in the frontend yet (the options list is currently read-only, per `MemoryVaultSlider.tsx`), so today this only affects the on-screen order of an inert `<ol>` - there is no `answer_index` for it to disturb. Each shuffled item still carries its `originalIndex` from the server payload regardless, so that submission logic (whenever it's built) has server-side option identity available from day one rather than needing a rework.
- **Failure handling (DoD item 2):** any QRNG failure - network unreachable, non-2xx (e.g. rate-limited), or a malformed/short payload - is caught inside `quantumShuffle()` itself and silently substitutes `Math.random()` per swap; it never throws and never blocks the vault card on the external call. Covered by dedicated tests simulating a rejected fetch, a 429 response, and a malformed body.
- **Demoability:** `MemoryVaultSlider.tsx` renders a small `⚛ Quantum-shuffled (ANU QRNG, live)` / `↻ Classical shuffle (quantum source unavailable)` indicator under the question so the live call is visibly verifiable on camera, not just narrated. Added the corresponding callout line to `docs/DEMO_SCRIPT.md` (no existing pitch-deck/demo-script file was found in the repo, so this doc was created rather than assumed).
- **Also fixed on this pass - unrelated build breakage found on inspection:** `vite.config.ts` imported `tailwindcss from '@tailwindcss/vite'`, a package not present in `package.json` at all (only `@tailwindcss/postcss` was), which broke `vite build`/`vite dev` outright with `ERR_MODULE_NOT_FOUND`. `main.tsx` also had a duplicate `import './index.css';`. Removed the unresolvable Vite-plugin import (this project's real Tailwind setup is the working `postcss.config.js` + `tailwind.config.js` + `@tailwindcss/postcss` route already in place) and the duplicate import. Verified with a clean `vite build`.
- **Testing standard (Rule 6):** added `lib/__tests__/quantumRandom.test.ts` (single-call batching, index-identity preservation, and every failure mode above) and extended `components/__tests__/MemoryVaultSlider.test.tsx` (quantum-shuffled render, classical-fallback render, and a no-question no-op case). Full suite, `tsc -b`, `eslint`, and `vite build` all pass with these additions.
